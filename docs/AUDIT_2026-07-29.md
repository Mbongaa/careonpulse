## HIGH

### Promote/demote org_admin — and every other membership mutation — is missing from /admin/gebruikers

- **Dimensie:** admin-completeness
- **Locatie:** `src/app/api/admin/users/route.ts:133`
- **Bewijs:** Spec §8 row 3: '/admin/gebruikers | Invite/create user (org + role), reset password, deactivate (ban), promote/demote org_admin'. The PATCH handler accepts exactly three actions: `if (!UUID_PATTERN.test(userId) || (action !== "reset_password" && action !== "ban" && action !== "unban"))` (src/app/api/admin/users/route.ts:133). The UI exposes only 'Wachtwoord' and 'Blokkeer/Deblokkeer' (src/app/(admin)/admin/gebruikers/_components/user-actions.tsx:46-63). Role is settable only at creation time (user-create-form.tsx:101-112 → route.ts:50). `/api/org/members` PATCH has the same three-action limit plus `invite_link` (src/app/api/org/members/route.ts:248), so no surface anywhere can write `organization_members.role`.
- **Impact:** An operator cannot promote a customer contact to org_admin after the account exists, cannot demote one who leaves that role, cannot move a user to a different organisation, cannot remove a user from an organisation, and cannot delete an account (only ban it). All of these are month-1 realities and all currently require direct SQL against careon-zsg.
- **Voorstel:** Extend the admin PATCH with `set_role` (org_admin|member), `move_org`, `remove_membership` and `delete_user`, each audited; refuse self-demotion and refuse touching the demo account, mirroring the existing ban guards (route.ts:137, 149).

### Audit log is missing 2 of its 4 promised filters, the two that exist are mutually exclusive, and only the newest 100 events are ever reachable

- **Dimensie:** admin-completeness
- **Locatie:** `src/app/(admin)/admin/activiteit/page.tsx:19`
- **Bewijs:** Spec §8 row 4: 'audit_events feed, filterable op org / gebruiker / actie / periode'. The page reads only `{ org, actie }` from searchParams (src/app/(admin)/admin/activiteit/page.tsx:19,25) — no gebruiker, no periode — and `recentAuditEvents` supports `userId` but nothing date-related (src/lib/careon-admin/admin.server.ts:125-139). Each filter chip href sets a single param and drops the other (`?org=${entry.id}` line 52, `?actie=${...}` line 65), so org+action can never be combined. The action chip list is derived from the *already filtered* result set (line 35), so selecting an org shows only that org's actions, and any action absent from the newest 100 rows never gets a chip. The result cap is hard-coded to 100 (line 30) with no pagination, offset, or 'load more'. Audit retention is 12 months (per §0 / CAREON_AUDIT_RETENTION_DAYS).
- **Impact:** The platform stores a year of audit history for AVG accountability but the only reader can see the most recent 100 rows. On a normal day of logins + state saves that is a few hours. Investigating 'what did user X do last Tuesday' — the primary purpose of the log in a healthcare context — is impossible through the product.
- **Voorstel:** Add date-range and user filters, make filters composable (build the query string from the current params instead of replacing it), and add offset/cursor pagination; derive the action chip list from a distinct-action query rather than the current page.

### Browser-local dashboard caches are not scoped to the logged-in account — org A's data is shown to (and can be written into) org B on a shared workstation

- **Dimensie:** auth-flows
- **Locatie:** `src/app/(main)/dashboard/_components/careon/careon-provider.tsx:136`
- **Bewijs:** Production/HR/middelen state is persisted under fixed, identity-free localStorage keys (`careon-production-v1` src/lib/careon-production/storage.client.ts:22, `careon-hr-v1` src/lib/careon-hr/storage.client.ts:7, `careon-middelen-v1` src/lib/careon-middelen/storage.client.ts:8) and `ProductionState` carries no org/user marker (src/lib/careon-production/types.ts:417-421). On mount the providers hydrate straight from that cache — `const stored = loadProductionState()` … `if (stored) { setProductionState(stored) … }` (careon-provider.tsx:136, 154-161), `const local = loadHrCache()` (careon-hr-provider.tsx:188), `loadMiddelenCache()` (careon-middelen-provider.tsx:220). The remote copy only wins when it is strictly newer (`isNieuwer`, careon-provider.tsx:166-174), and `/api/careon/production` returns `{ state: null }` for an org with no imports (src/app/api/careon/production/route.ts:121), so nothing ever overrides the stale copy. The caches are cleared only in `careonLogout()` (src/lib/careon-auth.ts:105-119) — never on login and never when a session simply expires or the browser is closed. The role dimension was handled (financial redaction of leftovers, careon-provider.tsx:106-154) but the organisation dimension was not. Worse, HR/middelen hydration pushes a *dirty* local cache to the server of whoever is logged in now: `if (local?.dirty) { if (local.revision === remote.revision) { … schedulePushRef.current(); } }` (careon-hr-provider.tsx:211-215, careon-middelen-provider.tsx:243-247).
- **Impact:** Clinic workstations are shared. User A (org A) works in the dashboard and closes the browser without using "Uitloggen"; user B (org B) logs in on the same profile and the dashboard hydrates org A's imported production records, HR figures and middelen inventory — cross-tenant disclosure of pseudonymised patient/production data. If A had an unsynced (dirty) HR or middelen edit and both orgs happen to sit on the same revision number (typical for fresh orgs: 0), B's session pushes A's data into org B's central Supabase record, corrupting another tenant's registration.
- **Voorstel:** Namespace the localStorage keys by the session's org/user id (or store the orgId inside the payload and discard on mismatch during hydration), and clear all careon-* local caches on successful login as well as on logout — not only in `careonLogout()`. Never push a dirty local cache without first verifying it originated from the current org.

### Cached production/HR/middelen data in localStorage is not scoped to user or organization and survives a session change

- **Dimensie:** pages-core
- **Locatie:** `src/app/(main)/dashboard/_components/careon/careon-provider.tsx:136`
- **Bewijs:** `CareonProvider` hydrates unconditionally from browser storage on mount: `const stored = loadProductionState()` (careon-provider.tsx:136), plus `loadAgendaFacts()/loadVerwijzersFacts()/loadToeslagenFacts()/loadDeclaratiesFacts()` (careon-provider.tsx:141-145). The storage keys are global constants with no org/user component — `careon-production-v1`, `careon-agenda-v1`, `careon-verwijzers-v1` (src/lib/careon-production/storage.client.ts:23, :83-84) — and `ProductionState` carries no org identifier at all (src/lib/careon-production/types.ts:417-421: only `fileName`, `importedAt`, `records`). Nothing validates that the cached import belongs to the currently authenticated org. The only place that wipes these keys is the explicit logout path `careonLogout()` (src/lib/careon-auth.ts:108-111); `careonSignIn()` (src/lib/careon-auth.ts:46-72) clears nothing on login. Worse, the remote copy only replaces the local one when it is strictly newer — `isNieuwer = Date.parse(remote.importedAt) > Date.parse(lokaal.importedAt)` (careon-provider.tsx:165-168) — so an older central import for the new org loses to the stale local one, and if the new org has no central data at all `fetchRemoteProductionState()` returns null (src/lib/careon-production/remote.client.ts:34-42) and the previous org's data simply stays on screen.
- **Impact:** On a shared clinic workstation: user A of org A activates production mode, then closes the browser or their Supabase session expires without ever clicking Uitloggen. User B (a different org, or a member of the same org) logs in on that machine and the dashboard immediately renders org A's pseudonymised ClientRecords, agenda aggregates and referrer network — labelled as their own live data, with the violet "Productie-data actief" banner naming org A's import file. Because local-wins-unless-newer, org B's own (older) central import never displaces it.
- **Voorstel:** Namespace the localStorage keys by the authenticated org/user id (e.g. `careon-production-v1:<orgId>`), or stamp `orgId` into `ProductionState`/aux facts and discard any cached blob whose org does not match `useCareonSessionInfo()`. Additionally call the same clear helpers on successful login in `careonSignIn()`, not only in `careonLogout()`.

### Unsynced manual HR/middelen registrations are silently destroyed on logout

- **Dimensie:** pages-added
- **Locatie:** `src/lib/careon-auth.ts:110`
- **Bewijs:** `careonLogout()` unconditionally calls `clearMiddelenState()` (src/lib/careon-auth.ts:110) and `clearHrState()` (:111), which remove both `careon-middelen-v1/-v2` and `careon-hr-v1/-v2` from localStorage (src/lib/careon-middelen/storage.client.ts:79-86, src/lib/careon-hr/storage.client.ts:73-80). Those caches are the ONLY copy of an edit whose central push has not succeeded: the providers keep `dirty: true` in the cache and retry with exponential backoff up to 60s (src/app/(main)/dashboard/_components/careon/careon-middelen-provider.tsx:153-160, careon-hr-provider.tsx:155-163), and while `syncStatus` is `"conflict"` no push is even scheduled (`if (!conflictRef.current) schedulePush()` — middelen provider:213, hr provider:181). There is no dirty-check, confirmation, or beforeunload guard before the clear.
- **Impact:** A user fills in the HR KPIs or assigns middelen while Supabase is briefly unreachable (status shows "fout") or while a colleague's edit produced a conflict, then logs out at the end of the day. All of that manual registration work — the only copy — is deleted with no warning and no way to recover it; on next login the page shows the last successfully synced (or seeded) state. Both pages are, by design, hand-maintained data with no other source.
- **Voorstel:** Before clearing, check the cached `dirty` flag (loadMiddelenCache()/loadHrCache()) and either (a) attempt a final synchronous flush, or (b) block logout with an explicit confirmation ("Er staan niet-gesynchroniseerde wijzigingen open"). At minimum, keep the dirty cache and only clear caches whose `dirty === false`.

### Financial role rule is app-layer only — RLS lets any org `member` read and overwrite the financial aggregates directly via PostgREST

- **Dimensie:** api-routes
- **Locatie:** `supabase/migrations/0010_org_scoping.sql:85`
- **Bewijs:** The client decision of 28-07-2026 ("members zien niets financieels") is enforced exclusively in route code: `src/lib/careon-production/aux-route.ts:60-62` nulls/hides the state on GET and `:76-81` returns 403 on POST for non-`org_admin`. The database does not encode the rule: `supabase/migrations/0010_org_scoping.sql:79-92` loops over `careon_declaraties_state`, `careon_toeslagen_state`, `careon_agenda_state` (and the rest) and grants `select, insert` to `authenticated` with policies `using (app.is_org_member(org_id) or app.is_superadmin())` / `with check (app.is_org_member(org_id))` — role-agnostic. No later migration narrows this (`0014_rename_org_tgc.sql`, `20260726175252_auth_security_hardening.sql:22-38` only touch orgs/profiles/chat tables). At the same time the PostgREST entry point is public: `src/lib/supabase/config.ts:8-9` reads `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY`, and that module is pulled into the client bundle through `src/lib/careon-auth.ts:7` ← `src/app/(main)/auth/_components/careon-login-form.tsx:1` ("use client"); grepping the built chunks in `.next/static/chunks` finds both `supabase.co` and the anon-key JWT prefix. The httpOnly cookies (`src/lib/supabase/server.ts:8-16`) stop XSS from stealing the session, but they do not stop the legitimate member from minting a JWT themselves.
- **Impact:** A regular `member` of the TGC organisation (someone who is supposed to see zero revenue data) can POST their own e-mail/password plus the bundled anon key to `https://<project>.supabase.co/auth/v1/token?grant_type=password`, then `GET /rest/v1/careon_declaraties_state?select=state` and `careon_toeslagen_state` / unredacted `careon_agenda_state`. That returns the complete invoice, toeslagen and omzet aggregates the UI, the data routes and the AI gate all deliberately hide. The same JWT also satisfies the INSERT policy, so the member can append a new row to `careon_agenda_state`/`careon_declaraties_state` that becomes the org-wide "newest wins" state — exactly the destructive scenario the comment at aux-route.ts:70-75 says the 403 prevents.
- **Voorstel:** Push the rule into RLS: add an `app.mag_financieel_zien()` security-definer helper (org_admin OR platform admin OR the fixed demo account, mirroring `src/lib/careon-financieel-rol.ts:16-18`) and rewrite the select/insert policies of `careon_declaraties_state`, `careon_toeslagen_state` and — for the omzet columns — `careon_agenda_state` to require it. Until that lands, treat the anon key as a member-reachable credential and assume every org member can read those three tables.

### Data-freshness columns for Agenda and Declaraties are permanently broken (query selects a non-existent `revision` column)

- **Dimensie:** admin-completeness · severity bijgesteld van high
- **Locatie:** `src/lib/careon-admin/admin.server.ts:169`
- **Bewijs:** `latestStatePerOrg()` always requests `select=org_id,saved_at,revision` (src/lib/careon-admin/admin.server.ts:169-171). Only two of the five state tables have a `revision` column: `careon_middelen_state` (added in supabase/migrations/0006_assistant_production_hardening.sql:6) and `careon_hr_state` (supabase/migrations/0007_careon_hr.sql:16). `careon_agenda_state` (supabase/migrations/0003_careon_agenda.sql:12-17) and `careon_declaraties_state` (supabase/migrations/0005_careon_declaraties.sql:8-13) never got one — migration 0008 only added `operation_id` to them (0008_runtime_operations_hardening.sql:108-111). - **Voorstel:** Make the column list per table (only request `revision` for `careon_middelen_state`/`careon_hr_state`), or add `revision` to the remaining state tables; and let `restGet` surface a failure state instead of collapsing 400/500 into `null`.
